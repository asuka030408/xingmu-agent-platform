# 星幕设备并发测试记录

测试日期：2026-11-20。对象：`E:\XingmuAgentPlatform` 本机演示服务和 PostgreSQL 数据库。测试前后均核对数据库预订总数与数据质量。

## 结果

| 场景 | 压力 | 实际结果 |
| --- | --- | --- |
| 同一预订凭证重复确认（HTTP） | 8 个同时请求 | 1 次写入，7 次返回原预订，0 错误 |
| 两个项目抢同一设备（HTTP） | 8 个同时请求 | 一个项目的 4 次请求返回成功或幂等；另一个项目 4 次返回 409；数据库只有 1 笔 |
| 两个项目抢同一设备（跨进程） | 8 个独立 Python 进程 | 1 次成功，7 次冲突，数据库只有 1 笔 |
| 同一凭证重复确认（跨进程） | 8 个独立 Python 进程 | 1 次写入，7 次幂等，数据库只有 1 笔 |
| 同一需求争抢数量 | 4 个独立进程争抢需求量 3 台 | 3 次成功，1 次冲突，数据库只有 3 笔 |
| 并发只读查询 | 60 次请求，20 个工作线程 | 全部 HTTP 200；本次测得第 95 百分位约 0.072 秒，最慢约 0.078 秒 |
| 读流量与预订限流 | 先 60 次读，再并发 32 次预订方案请求 | 读全部 200；预订方案 30 次 200、2 次 429，符合每分钟 30 次的配置 |
| 绕过应用直接插入重叠预订 | 用预订数据库账号直接写入 | PostgreSQL 排斥约束拒绝，未新增记录 |

测试中的预订均按请求编号清理。预订总数测试前后都是 **3 笔**，`/api/quality` 和 11 项自动测试均通过。

## 测试时发现并修复的问题

原有限流计数把查询和预订放在同一个桶里。查询流量一高，预订会被误判为超限。现按本机来源与请求类别分别计数；新增自动测试覆盖“60 次读请求后仍能生成预订方案”。

## 这次测试的范围

这次验证了本机单实例服务、跨 Python 进程的数据库争抢、数据库最终约束和请求上限。它没有模拟多台应用服务器、真实网络延迟或长时间持续负载。接入真实企业业务前，仍需按预计用户数做容量测试。
